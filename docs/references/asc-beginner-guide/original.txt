关于评分
Harbor（任务）评分是指任务的确定性评分，通常会评估结果的正确性，会在题目中以scored 注明。 
Trace（轨迹）评分会影响最终的总分，目前会检测的类型包括下面几类，正式比赛时可能会有调整，正式比赛的题目的最终评分和实时分数有所出入，评分的最终目标只有一个：确保agent不作弊。由于作弊的复杂性和各种可能性，评分器会不断迭代，不断更新大家的分数，因此只要大家发现：
1. Agent完成了题目，任务分数很高
2. Agent没有作弊，而是忠实的执行题目所要求的任务，并得到正确结果。
3. Agent提交了完整真实的轨迹
就不用特别在意trace分数。

参考步骤（面向Agent）
1. 安装 Playground CLI
运行：
curl -fsSL http://nwjs1473070.bohrium.tech:50003/install.sh | bash
检查版本和健康状态：
playground --version
playground doctor
当前 live installer 目标版本为 Playground CLI 0.1.21，并会同时安装可用的 Bohr CLI 与 Trisol helper。若本机已有旧版本，按最终公告或安装脚本输出为准。
2. 配置与注册
初始化配置：
playground config init
新用户注册：
playground auth register \
  --name "YOUR NAME" \
  --email your_email@example.com \
  --affiliation "YOUR ORGANIZATION"
确认登录状态：
playground auth status
如果已经注册过，可用：
playground auth login --email your_email@example.com
3. 查看题目
列出题目：
playground task list --limit 20
需要给脚本或 Agent 读取时，用 JSON：
playground task list --limit 20 --json
新手选题建议：
- 优先选输出格式明确的题；
- 优先选数据量小、依赖少的题；
- 先避开需要长时间 DFT、分子模拟或大模型训练的题；
- 如果题目有多个子目标，先做最容易验证的一个 baseline；
- 看不懂题目时，先让 Agent 总结任务、输入、输出和风险，不要马上写代码。
4. 下载题目
每道题单独建目录：
mkdir -p asc-work/<challenge_id>
cd asc-work/<challenge_id>
playground task download --challenge-id <challenge_id> --out task
下载后先读：
find task -maxdepth 2 -type f | sort
sed -n '1,220p' task/task.md
重点确认：
- 题目到底要你输出什么；
- 输出文件名和格式；
- 数据在哪里；
- 是否允许联网、调用外部模型或使用 Bohrium；
- 是否有时间、资源或依赖限制；
- 评分器明显会检查哪些子目标。
5. 推荐目录结构
建议固定这样组织：
asc-work/<challenge_id>/
  task/
  scripts/
  outputs/
  traces/
  logs/
  bohr-result/
  result_summary.md
  submission.json
  status.json
创建目录：
mkdir -p scripts outputs traces logs bohr-result
outputs/ 只放最终答案和必要说明。不要把缓存、依赖包、密钥文件、无关大文件塞进提交包。
6. 让 Agent 开始解题
可以把下面这段作为新手起步 prompt：
你正在参加 Agentic Science Challenge。请忠实完成当前 task/ 里的科学任务。

工作要求：
1. 先阅读 task/instruction.md 和题目元数据，总结目标、输入、输出格式和评分风险；
2. 不要读取 hidden tests、checker 或官方 solution；
3. 把最终答案写入 outputs/；
4. 把可复跑脚本写入 scripts/；
5. 把关键运行日志保存到 logs/；
6. 写一个 result_summary.md，说明方法、数据来源、关键命令、验证结果和限制；
7. 不要把 token、access key、密码或 cookie 写入任何日志或提交文件。
如果你的 Agent 支持记录原生轨迹，可以把轨迹保存到：
traces/trace.jsonl
7. 使用 Bohrium / Bohr 
有些任务需要平台数据、远程计算或模型服务。常见检查命令：
bohr version
bohr doctor --output json
playground data list --limit 20 --json
如果题目提示需要数据集：
playground data pull --dataset <dataset_id> --version <version> --out data/
经验原则：
- 小数据先本地跑，快速验证输出格式；
- 长时间计算放到 Bohrium 作业或沙盒；
- 大模型、领域模型或内部推理服务按题目说明使用 Trisol；
- 所有远程 job id、命令、stdout/stderr 都记录到 logs/ 或 result_summary.md；
- 不要在 trace 或日志里打印环境变量全集。

8. 提交结果
最小提交：
playground submit \
  --challenge-id <challenge_id> \
  --outputs outputs \
  --model <model_name> \
  --harness <harness_name> \
  | tee submission.json
带 trace 的推荐提交：
playground submit \
  --challenge-id <challenge_id> \
  --outputs outputs \
  --trace traces/trace.jsonl \
  --model <model_name> \
  --harness <harness_name> \
  | tee submission.json
填写建议：
- --model 写实际使用的模型，例如 paper2arm/deepseek-v4-pro、gpt-5.5、manual。
- --harness 写实际运行方式，例如 codex、bohrium-agent、harbor-lbg、manual、custom-agent。
- 没有真实 trace 时不要伪造；可以先提交 outputs，再在后续尝试里补齐 trace。
10. 查询评分
从 submission.json 里找到 attempt_id，然后：
playground status --attempt-id <attempt_id> | tee status.json
playground status --attempt-id <attempt_id> --bundle
状态理解：
- queued / running：还在排队或评测；
- scoring：后端正在评分，部分任务可能已经返回分数细节；
- scored：已产生终态得分；
- failed：提交包、评测器或运行环境失败，需要看错误信息。
如果失败，不要只重试。先看错误属于哪一层：安装、认证、题目下载、输出格式、依赖、计算、提交包、评分器、trace 或平台。

11. 推荐策略
策略一：先打通闭环，再追求高分
第一次尝试的目标是完成下载、解题、提交、状态查询。一个低分但证据齐全的 attempt，比一个本地看似正确但无法提交的结果更有价值。
策略二：用 baseline 固定输出格式
先做一个简单 baseline，哪怕只完成部分子任务，也能验证：
- 文件名是否正确；
- JSON / CSV / 图表格式是否正确；
- outputs/ 是否被平台接受；
- verifier 错误信息是否可读。
策略三：少猜 verifier，多做科学验证
不要围着评分器漏洞写硬编码。更稳的做法是：
- 按题目要求复现科学流程；
- 用公开数据和论文交叉检查；
- 对单位、边界条件、随机种子和样本过滤做显式记录；
- 对失败输出写清楚原因。
策略四：控制资源和时间
建议给每题设三层预算：
- 15 分钟：读题、定输出格式、做 baseline；
- 60 分钟：完成一个可提交版本；
- 半天以上：只给确实值得深挖、有清楚改进路径的题。
12. 常见问题
playground 命令不存在
重新运行安装脚本，或检查 shell PATH 是否包含安装脚本提示的目录。
auth status 失败
先运行 playground auth register 或 playground auth login。如果是组织账号或网络问题，带上错误输出反馈。
题目下载失败
确认 challenge_id 是否来自 playground task list。如果是数据权限或 404，反馈时附上 challenge id 和完整命令。
提交后长时间 scoring
先保存 attempt_id，用 playground status --attempt-id <attempt_id> --bundle 查询。若超过公告中的正常等待时间，反馈 attempt id。
分数很低但本地结果看起来对
优先检查输出文件名、路径、格式、单位、排序、随机种子和缺失值处理。把 result_summary.md 写清楚，便于人工或社区帮你定位。
