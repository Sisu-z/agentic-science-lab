# 临时团队与派工约定

## 按当前任务使用四种职能

| 职能 | 交付责任 | 何时启用 |
| --- | --- | --- |
| 总监（当前主聊天） | 提炼目标、核规则、派工、管理时间、接受交付、统一汇报 | 整个比赛窗口 |
| 平台与交付执行 | 账号/工具预检、合法打包、真实轨迹校验、提交回执与评分定位 | 准备及提交阶段 |
| 当前题执行 | 按题面提出路线、完成实际实现/计算、验证与失败记录 | 规则及输入就绪后 |
| 独立验证 | 对准确版本作不同路径的正确性、合同和复现检查 | 首次有效基线与交付前 |

这是弹性职能，不是固定四名员工。本宿主当前最多四个并发上下文（含总监），必要时结束准备运行再派解题任务。一般只开一条主实现线；独立问题可以并行调查，接口未定时不让多个成员同时改公共文件。

平台上“最多五个本人绑定 Agent”不等同于 Codex 的五个聊天/子上下文。当前仅确认已有本人 Agent 归属有效；不得把内部角色数写成已登记账号数。正式贡献者身份、原生轨迹如何随包被消费，先按当前官方工具核实；未验证时收敛为一个已绑定执行身份和可审计的执行路径。

当前 CLI 不自动归并 Codex 子成员轨迹，因此每道正式题指定一个主要实现者，在新的任务上下文只加载合同和必要材料，保存并提交该次完整真实原生记录。其他成员优先只读核查；实现者读取反馈后实际修正、复跑并留下记录。协助记录另行保留，不宣称主记录自动覆盖其全部动作；若要由多个成员共同产生交付物，须先验证官方支持的证据路径。

## 一项任务，一个当前授权运行

总监在 Issue 头部写目标、修订、唯一 `run_id`、有效基线、依赖、可改范围、产物、验收、投入上限和停止条件。执行者先读取该记录；无分配者不得抢单。总监负责把内部委派回填到 Issue，维护者不用搬运。

- GitHub Issue：唯一实时任务状态，评论保存进展、失败与接受决定。
- PR：候选改动及准确提交的审查记录；`main`：已接受的公开基线。
- 受控本地材料：实际赛题、源码、数据、原生轨迹和个人文件；不复制一份竞争的任务状态表。
- 正式提交：总监指定唯一操作者；同一账号、输出目录或提交动作串行处理。

研究者只读或写自己的报告；实施者在独立 clone/worktree 或分配目录工作；不同运行不修改同一目录。共享工具/账号不提供硬隔离，遇冲突先停止旧写入运行再换人。

## 成员回填格式

每次报告不超过必要长度，但必须包含：任务 ID/修订/run_id、依据版本、实际产物、做过的验证与结果、未验证项、当前阻塞、下一项能区分原因的检查。用“设想／已实现／本地验证／已提交／平台终态”准确区分层级。

一次实验只改变少量明确因素，预先写预期信号和检查时点。连续两轮无新增证据时，总监要求重新核对理解、输入、方法、实现和验证，不默认加长训练/搜索。不因失败次数本身丢弃仍有收敛证据的路线。

## 复核与接受

验证者读取原任务、当前合同、准确提交、输入校验值及原始检查结果。阻塞缺陷必须解决；风格和无关重构不得拖住交付。总监核对材料后接受，并在 Issue 写明证据；关闭 Issue 不自动等于通过。

发现规则、资源或输出合同变化，更新原 Issue 修订和受影响验收。替换成员时保存失败记录、使旧 run_id 失效、登记新运行。正式评分未知就保留待评测，不能把已上传或队列中的 0 分写成通过或最终失败。
