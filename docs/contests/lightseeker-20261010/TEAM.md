# 项目内可见对话协作

方法基线为 [project-team-playbook v0.1.0](https://github.com/Sisu-z/project-team-playbook/tree/20b9926b99415a6cec9ea0af4dc09ca71ac2a277)。成员入口见 [START_HERE.md](START_HERE.md)。

## 职责与工作位置

| 职责 | 承载对话 | 交付责任 |
| --- | --- | --- |
| 总监 | 用户指定的本主对话 | 整理目标、登记分配、查规则、协调依赖、审查接受、汇总经验及交付节奏 |
| 单题主要实现 | 用户在“全栈开发”项目里开的题目对话 | 理解本题合同、实际实现、执行、自检、保存真实证据并回填原 Issue |
| 单题协作/独立复核 | 同题第二个可见对话，按需 | 明确范围的调查或对确切候选做独立检查，回填同一个 Issue |

不设固定员工数，不用内部子 Agent 代替用户要求的可见对话。此前内部准备运行只作为历史准备证据，不算已建立的单题成员。总监不自行创建新对话或向其他对话发消息；使用相应宿主能力须有用户明确授权。

## 一题一个当前运行，可有不同协作职责

GitHub Issue 是唯一实时任务源。头部写目标、修订、当前主要实现对话、协作对话及各自范围、唯一 run_id、基线、依赖、可改范围、产物、验收、投入和停止条件；评论保留承接、进展、交接、审查与接受历史。总监串行确认分配。

一题只有一个当前主要实现者；同题第二个对话可以调查或独立审查，不重复领取主实现。不同题可并行实施，分别使用独立目录；共享文件、同一账号操作和正式提交串行。对话名字、GitHub 账户及平台参赛 Agent 是不同标识，不把对话数量说成已绑定参赛账号数量。

用户更换对话时，总监先停止/确认旧运行停止，保存可接手检查点、作废旧 run_id，再登记新运行。新对话先重读 Issue 和真实证据，不能冒用前任的原生记录。

## 共享信息和跨题经验

共同背景、规则和流程在本目录；当前行动与阻塞在 Issues；复用入口在 [EXPERIENCES.md](EXPERIENCES.md)。不假定项目中的对话已经读过彼此聊天，也不以项目记忆代替当前任务核对。

成员遇到工具问题、输出合同变化或与别题相关的经验，在原 Issue 回填来源、环境、实际证据、适用边界和受影响任务。总监将可公开复用项加入经验索引，并在关联 Issue 登记影响；不要求用户转发报告。题目间可以共用已验证的方法，不共用可变目录或将未授权答案公开。

## 交接与接受

使用 [TASK_TEMPLATE.md](TASK_TEMPLATE.md) 的回填和交接格式。至少留下准确产物版本/校验值、输入与环境、运行入口、实际成功和失败检查、未覆盖项、下一动作及停止条件。受限正文只保存本地检查点，公开 Issue 留材料键。材料索引只解析位置，不复制状态。

审查者读取原任务、合同、确切候选与实际证据。主要实现者据反馈修正并复跑；总监接受后在 Issue 写证据。PR 是候选，main 是已接受的公开基线；关闭 Issue 不自动等于解题通过。平台排队、已上传、本地正确和最终得分分别报告。

各对话保存自己的完整真实原生记录；不假定 CLI 自动合并不同对话或内部子日志。多对话共同产生交付物时，先核官方支持的贡献证据路径；未验证时由一个主要实现对话完成可追溯实现、修正与复跑，协作证据另行保留。
