# 协作复盘与下次采用方式

复核日期：2026-10-11。范围是组织、交接和交付流程；比赛作答窗口已经结束。本页不维护第二份成绩表，不公开正式题面、解题实现、答案、个人材料或原始轨迹。

## 应继续保留的协作方式

- 用户给目标、作关键选择，总监自行读任务与证据、派工、验收和整合，用户不搬运成员报告。
- 专业实现采用用户可见的独立聊天；一题一位主要实现者，必要时增加范围明确的独立复核。临时角色按需要启用，聊天数量不是产出指标。
- Issues 保存唯一当前任务，文件和原始证据留受控共同位置。跨题共享平台操作和排错经验，不靠聊天自动互读，也不复制实时状态。
- 已授权的提交、查分及按实际反馈返修正常推进。排队占位零分不触发同版重交；最佳正式版本与最新接收版本分别保留。

这些做法在本次获得了实际交付与接手证据，但没有做效率对照试验，不能据此量化提效或证明对所有项目都有效。

## 必须改变的地方

| 实际摩擦 | 下次操作 | 验收依据 |
| --- | --- | --- |
| 必做个人材料拖到最后窗口才收口 | 启动时在原任务登记全部资格、身份、材料和必做项的负责人、证据与目标接收时间；保留必要本人操作的余量。主攻题可并行，但扩题不能掩盖未收口门槛 | 原任务有接收回执或明确阻塞与下一步；账号归属、材料接收、招聘系统关联分别核对 |
| 简单材料提交另建聊天，增加上下文、等待和交接 | 授权明确、输入齐全、步骤确定的上传、填表、核回执由总监直接处理；确需持续专业实现、资源隔离或独立验证时再派工 | 不为已有授权重复批准；不为组织形式增加一次等待；仍保留真实记录与接收证据 |
| 默认分类的可见聊天被误以为已归入项目或是临时聊天 | 创建时核宿主是否支持项目归属，并分别登记对话标识、工作目录、项目标签和材料入口。能力不足时明确说明，用共同任务源补足协作 | 不能用相同目录、分支或聊天标题代替项目标签核验；不直接修改应用数据库 |
| Issue 新评论与旧头部相互矛盾 | 恢复、停止、接收和接受时同步当前头部；旧决定转为有日期的历史。其他文档链接原 Issue | 新成员只读当前头部和相关回执即可知道是否可开工；提交暂停不能在接收后继续冒充现状 |
| 增加执行聊天后，审查、打包、上传和评测成为瓶颈 | 按计算资源、审查吞吐、上传和排队情况限制在制量；先交可验证基线，再做有证据的改进 | 候选到接收的等待和未验收积压可查；没有新证据就停止扩张或重试 |

个人材料的授权与明确暂停仍由本人决定；提前收口不等于可以代替本人确认。恢复办理时沿用仍有效的明确授权，不凭经过了时间推定批准。

## 原生记录与复现的经验边界

本次工具链中，作者在运行中自行复制记录可能漏掉正在执行的工具回执。需要完整原生证据的版本，作者完成工作并正常结束后，由总监从稳定的连续记录封存；如恢复原作者提交，提交后的记录另存，不伪装成此前已有的科学证据。保留所有真实失败、调用结果和没有调用编号的派发封装；不合并不同作者的轨迹冒充独立完成。

上传前核实际压缩包、原生与结构化记录、模型及 harness、manifest、入口和产物。文件重建与完整科学复算分别标明；CLI 自动生成的耗时或声明字段不冒充实测。结构检查通过也不能证明评分失败的根因。具体版本与已执行方法见 [平台手册](PLATFORM.md#已完成版本的原生记录与复现)。

## 结束后的整理

先确认所有执行已停止、已接收版本及未出终分项有交接，再选择性归档聊天。聊天归档、删除聊天、删除工作目录和清理缓存是不同动作；归档不承诺释放多少磁盘或内存。原始证据、最佳版本和接收回执保留到复核需要结束。

空间与环境审计记录留在本机：分别量磁盘实际占用、进程内存、运行中任务、隔离环境和共享缓存。有无赛前基线决定能否归因净增量，不能将所有缓存或文件大小说成本次下载流量。资源足够时不为整理而删除项目内容。

## 回流到通用指南

上述经验用于升级 [project-team-playbook](https://github.com/Sisu-z/project-team-playbook)：强化总监的门槛收口、直接执行简单事务、授权传递、真实交付与项目结束检查。通用指南不搬入本届题目、账户、时间表或专有评分规则。

本届执行时仍锁定原采用版本，不把赛后新指南追认为比赛期间已采用的规则。下一项目从新版本入口启动，既有项目按实际影响选择升级。
